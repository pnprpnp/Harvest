# Harvestnavi relay

Cloudflare Worker と D1 を使い、記録を高速に遠隔保存してから既存の
Apps Scriptへ転送します。中継サーバーが停止している場合、アプリは従来の
Apps Script直接送信へ自動的に戻ります。

同じWorkerで、生育予測に使う気象庁の過去観測値と予報もD1へ保存します。
アプリで一度気象地点を登録した後は、定期処理が気象データを差分更新するため、
更新のためだけに毎日アプリを起動する必要はありません。

## 初回設定

1. `relay` ディレクトリで `npm install` を実行します。
2. `npx wrangler login` でCloudflareへログインします。
3. `npx wrangler d1 create harvestnavi-record-relay` を実行します。
4. 表示された `database_id` を `wrangler.jsonc` へ設定します。
5. `npm run migrate:remote` でテーブルを作成します。
6. 次のSecretを登録します。

```sh
npx wrangler secret put RELAY_TOKEN_SHA256
npx wrangler secret put APPS_SCRIPT_URL
npx wrangler secret put APPS_SCRIPT_TOKEN
```

- `RELAY_TOKEN_SHA256`: 現在のアプリ連携トークンをSHA-256で変換した64文字の値。元のトークンは保存しません。
- `APPS_SCRIPT_URL`: 現在利用中のApps Script WebアプリURL。
- `APPS_SCRIPT_TOKEN`: Apps Scriptの `setupHarvestWorkerApiToken()` で発行する、記録操作だけを許可した制限トークン。

7. `npm run deploy` を実行します。
8. アプリの「Google連携設定」に、発行されたWorker URLを「高速受付URL」として保存します。

## 動作

- Workerは記録をD1へ保存した時点で受付完了を返します。
- Apps Scriptへの転送はレスポンス後に行います。
- 通信失敗時は1分ごとの定期処理がD1の未反映記録を再送します。
- 完了・失敗データは30日後に削除します。
- 同じ受付IDの再送は重複登録しません。
- 気象データは、初回に必要期間を遡って取得し、その後は予報を6時間ごとに更新します。過去観測値は直近8日分を再取得し、遅れて公開された値や訂正値も取り込みます。古い欠損は1日1回、最大31日間の区間を順番に再取得します。
- 気象庁への過度なアクセスを避けるため、地点ごとのD1キャッシュを端末間で再利用します。
- 気象データの取得失敗時は5分後、15分後、以後1時間ごとに間隔を広げて再試行します。
- 過去の日照時間は元の時間数を保存し、従来式との互換用に8時間を基準とする日照係数も保存します。予報の天気コードから作る係数は日射量の実測値ではありません。日照時間も地点・日付によって気象庁の推計値を含み得るため、`sunshineSource` は `jma-reported-duration` とします。現在の取得CSVには品質フラグがないため、`quality` には品質未確認または欠損を明記します。
- 予報の日別値には使用した予報の発表時刻 `issuedAt` と実取得時刻 `retrievedAt`、気温・日照の推定方法と補完有無を保存します。過去観測値にも実取得時刻を付けます。以前のキャッシュで時刻が不明な値へ取得時刻を補いません。
- `/weather` は`schemaVersion:5`で既存項目を維持し、`weatherPolicy`、`fallbackErrors`と日・項目別の出所を追加します。正常なJMA項目は維持し、過去の欠損だけNASA POWER、今日・未来のJMA予報範囲内の欠損だけMET Norwayで補完します。今日の時間別JMA観測も確認します。`historyCoverage`は補完前のJMA欠損を保持し、気象庁への再確認を続けます。APIの非公開キャッシュは端末に送りません。D1の表構造は変更しません。
- 更新の診断用に `refreshStatus`、`lastError`、`lastAttemptAt`、`nextAttemptAt` も返します。欠けた日や不足項目はアプリが予測と同じ気象入力から導出し、取得失敗時も保存済みデータと失敗理由を併記します。
- 過去予報の全発表版はこの中継キャッシュでは保存しません。アプリ側で取得時のスナップショットを蓄積し、検証基準日以後に発表・取得した情報を過去予測へ混ぜないようにします。

補完式・単位・API条件・キャッシュ・未補完となる場合は[気象データの欠損補完](../docs/WEATHER_FALLBACK.md)を参照してください。追加APIキー・Secret・D1移行は不要です。

## 記録の中継受信（試作）

管理者の記録受信は、高速受付URLの `/records` を先に試します。中継はGoogleが返した確定済みの同期応答をD1の `relay_record_sync_pages` へ保存し、同じ同期番号・カーソル・旧苗植え記録の補完条件なら最大60秒間再利用します。送信待ちの内容を受信用データへ混ぜません。全履歴の永続ミラーではなく、受信ページと「確認済み同期番号まで変更なし」の応答を共有する試作です。

- コピーがある場合はGoogleの記録取得を待たずに返します。アプリは受信後にGoogleの同期番号を裏で確認し、中継の確認時刻と確認中・最新確認済み・新しい変更あり・確認失敗を表示します。変更があれば通知ドットを点け、次の受信は `forceFresh` で取り直します。確認が終わる前に中継の結果を「Googleと同期済み」とは表示しません。
- 初回、未保存の差分、期限切れ、条件が違うページはGoogleへ問い合わせます。中継は4秒で待ちを打ち切って既存の直接受信へ戻れます。中継側の取得は `waitUntil` で続けて、次回のために準備します。初回の遅い応答では、Googleへの取得が一度重複することがあります。
- 元のGoogle連携URLと中継の `APPS_SCRIPT_URL` が一致し、高速受付の認証ハッシュと管理者の連携トークンが一致する場合だけ利用します。Googleへの取得には利用者のトークンを使い、Googleの管理者限定の閲覧確認を維持します。既存の制限付き `APPS_SCRIPT_TOKEN` に全履歴の閲覧権限を追加しません。トークンの原文を受信キャッシュへ保存しません。
- 接続先・認証ハッシュ・利用者トークンのハッシュを分け、同期番号、両方のカーソル、取得上限、苗ロス率・苗の配列・ベッド別植え数の補完条件もキャッシュキーへ含めます。旧記録の復元結果を別条件へ流用しません。
- 送信受付時とGoogleの本体反映完了時に `relay_record_sync_state` の世代を進めます。古い世代の取得処理が後から終わっても、現在の受信結果を上書きできません。同じ世代でも古い取得開始時刻・同期番号の応答を新しい応答へ上書きしません。スプレッドシートの直接編集は既存の同期番号トリガーと、受信後のGoogle確認・60秒の期限で検出します。
- 保存は最大64ページ、1ページはUTF-8で1MBまでです。大きいページはGoogleの結果を返し、保存だけ省きます。既存の毎分処理で確認から2分以上経過したコピーを整理します。初期設定不足、上限、通信失敗、不正応答では直接受信へ戻します。作業者モードの計算用受信は従来どおりです。

本番へ反映する場合は、先に既存D1へ追加テーブルを作成してからWorkerを更新します。既存の営農記録・送信待ち・気象テーブルは変更しません。Apps Scriptの更新と追加Secretは不要です。

```sh
npm run migrate:remote
npm run deploy -- --keep-vars
```

Workerを旧版へ戻すと `/records` が未対応になるため、アプリは従来の直接受信へ戻ります。本番デプロイとD1移行は明示依頼がある場合だけ実施します。

無料枠は既存アカウント全体で共有されます。2026-10-02に確認した[公式D1料金](https://developers.cloudflare.com/d1/platform/pricing/)ではFreeの読込みは500万行/日、書込みは10万行/日で、超過するとクエリが失敗します。[公式D1制限](https://developers.cloudflare.com/d1/platform/limits/)と[利用規約](https://www.cloudflare.com/terms/)も確認しています。新しい有料サービスやプラン変更は追加せず、保存件数・サイズ・期限と索引を限定し、上限で利用できない場合はGoogle直接受信へ戻します。契約済みプランの変更は行いません。

中継の新規テストは `node:sqlite` で実際のSQLも検証します（Node 24で確認）。期限、権限、接続先・補完条件の分離、同時更新、送信完了後の無効化、容量超過・保存失敗、64ページ上限、期限切れ整理を対象にしています。
